## شواهد تأییدشده

### CI و Production
در Run تأییدشده بالا، تست‌ها، TypeScript، Lint، Build، Deploy به Cloudflare، smoke test دامنه‌ها و Browser runtime smoke موفق بودند. یک Run پیشین، [38576196411](https://github.com/mohsendarbandi-maker/customs-os/actions/runs/38576196411)، فقط در آزمون کنترل Service Worker شکست خورد؛ Run بعدی موفق شد. منطق آزمون مرورگر در تغییر نگهداری جاری اصلاح می‌شود تا ابتدا فعال‌شدن Service Worker را اثبات کند و سپس در صورت نیاز یک بار صفحه را بارگذاری مجدد کند؛ نتیجهٔ Run این تغییر باید جداگانه بررسی شود.

از این محیط، مرورگر زندهٔ مستقل قابل اجرا نبود؛ بنابراین آزمون دامنه به شواهد GitHub Actions متکی است، نه ادعای مشاهدهٔ دستی.

### Supabase — داده و دسترسی
- آخرین Migration اعمال‌شده در DB: `20261014141346_workspace_complete_reminder_team_scope`
- شمار داده‌ها هنگام ممیزی: ۳۱ یادآور، ۹۰ رکورد تحویل اعلان، ۳۱ گفت‌وگو و ۸۲ پیام.
- در زمان ممیزی، ۳۱ یادآور `private` و صفر یادآور `team` وجود داشت.
- جدول‌های اشتراک صریح `reminder_shares`، پیوند کار به گفت‌وگو و فعالیت کار هنوز ساخته نشده‌اند.

### تغییر امنیتی اول — ACL توابع چت
Migration `20261014110520_workspace_chat_rpc_acl_hardening` در Production اعمال شد.
- `chat_mark_played(uuid)`: اجرای `PUBLIC` و `anon` رد شد؛ اجرای `authenticated` حفظ شد، چون بدنهٔ تابع عضویت کاربر در گفت‌وگو را اعتبارسنجی می‌کند.
- `prepare_chat_attachment_security()`: اجرای مستقیم از `PUBLIC`، `anon` و `authenticated` رد شد؛ Trigger واقعی روی `chat_attachments` همچنان متصل است.
- مجوزها با `has_function_privilege` و وجود Trigger با SQL خواندنی تأیید شدند.

### تغییر امنیتی دوم — حذف دسترسی و اعلان سراسری برای یادآور team
Migration `20261014140105_workspace_reminder_team_scope_hardening` در Production اعمال شد.
- سیاست‌های SELECT/UPDATE/DELETE برای `operational_reminders` فقط مالک/مدیر مجاز، ایجادکننده یا مسئول را مجاز می‌کند؛ مقدار `visibility='team'` دیگر به‌تنهایی دسترسی برای همهٔ کارکنان سازمان ایجاد نمی‌کند.
- Trigger تحویل یادآورها دیگر تمام کارکنان سازمان را دریافت‌کنندهٔ اعلان نمی‌کند؛ تا زمان پیاده‌سازی اشتراک صریح، اعلان به مسئول واحد کار محدود است.
- تابع و Trigger جدید با SQL خواندنی بررسی شدند و هنگام تغییر هیچ یادآور `team` موجودی در Production نبود.

### آزمون RLS در تراکنش‌های برگشت‌خورده
- شبیه‌سازی نقش دیتابیسی `authenticated` با JWT claim مالک: ۲۹ یادآور خصوصی فعال/باز قابل مشاهده بود.
- همان آزمون برای کارمند عادی همان سازمان: صفر یادآور خصوصی قابل مشاهده بود.
- یک رکورد آزمایشی `team` در تراکنش موقت ساخته شد؛ کارمند نامرتبط صفر رکورد و صفر تحویل اعلان مربوط به آن دید؛ تراکنش با `ROLLBACK` تمام شد و دادهٔ آزمایشی باقی نماند.
- این آزمون‌ها دسترسی دیتابیسی/RLS را ثابت می‌کنند، اما جای آزمون کامل از طریق نشست واقعی REST API برای تمام نقش‌ها را نمی‌گیرند.

### تغییر امنیتی سوم — بستن مسیر RPC تکمیل یادآور
Migration `20261014141346_workspace_complete_reminder_team_scope` در Production اعمال شد.
- تابع `complete_operational_reminder` از نوع `SECURITY DEFINER` دیگر برای نقش‌های غیرمسئول، صرفاً به‌خاطر `visibility='team'` اجازهٔ تکمیل نمی‌دهد؛ مالک/مدیر مجاز، ایجادکننده یا مسئول همچنان مجازند.
- با تراکنش آزمایشی، یک یادآور team موقت توسط مالک ایجاد و تلاش کارمند نامرتبط برای تکمیل از RPC آزموده شد؛ فراخوانی با پیام «یادآور پیدا نشد یا دسترسی تغییر آن مجاز نیست» رد شد و تراکنش با `ROLLBACK` پایان یافت.
- مجوز RPC برای `authenticated` حفظ و برای `anon` غیرفعال باقی ماند؛ منطق تکرار و جلوگیری از ایجاد نوبت تکراری حفظ شده است.

### بازبینی هشدارهای Advisor
- ۱۵ جدول دارای RLS ولی بدون Policy بررسی شدند؛ هیچ‌کدام از نقش‌های `anon` و `authenticated` مجوز SELECT/INSERT/UPDATE/DELETE نداشتند. تا زمان بررسی مسیرهای backend، برای رفع هشدار صرفاً Policy عمومی اضافه نمی‌شود.
- هشدارهای باقی‌ماندهٔ Security Advisor شامل توابع `SECURITY DEFINER` قابل اجرا توسط `authenticated`، محل نصب `pg_net` در `public` و تنظیم محافظت رمزهای لو‌رفته است. توابع RPC باید یک‌به‌یک با بدنه و مسیر واقعی فراخوانی بررسی شوند؛ revoke گروهی انجام نشده است.

## تطبیق Migrationها

تاریخچهٔ Production و فایل‌های مخزن برای سه تغییر customs با شناسه‌های متفاوت ثبت شده بود و یک تغییر میانی در مخزن به فایل دیگری ادغام شده بود. بر اساس تاریخچهٔ commit و محتوای SQL، نگاشت زیر بازیابی می‌شود:
- `20261013151846_customs_procedure_state`: فقط ستون `procedure_state` و توضیح آن.
- `20261013152021_customs_export_workflow_stages`: چک‌کانسترینت مرحله‌های گردش‌کار صادرات.
- `20261013164306_customs_temporary_import_stages`: افزودن مرحله‌های تضمین، دورهٔ استفاده و خروج مجدد.
- `20261013180308_customs_workflow_procedure_state_audit`: Trigger و تابع تاریخچهٔ ممیزی.

فایل‌های محلی با شناسه‌های Migration ثبت‌شده در Production هم‌تراز شده‌اند؛ تطبیق مجدد ۲۴۶ فایل Migration و ۲۴۶ رکورد تاریخچه را بدون نسخهٔ کم/اضافه نشان داد. Migration قبلی دوباره روی Production اجرا نشده است.

## تغییرات آخرین نوبت
- دو Migration امنیتی یادآورها/چت اعمال و ACL، Trigger و RLS بازبینی شدند.
- آزمون نقش دیتابیسی مالک/کارمند و آزمون موقت team با `ROLLBACK` اجرا شد.
- تطبیق نگاشت Migrationها و پایدارسازی انتظار Service Worker در تست CI در تغییر نگهداری جاری قرار گرفته است.
- هیچ تغییر UI یکپارچه‌سازی Chat + Reminders در این نوبت ادعا نمی‌شود.

## دقیقاً سه اقدام بعدی
1. پس از CI این تغییر نگهداری، تطابق نسخه‌های Migration فایل/DB و سلامت Production را دوباره بررسی و نتیجه را ثبت کن.
2. ماتریس REST API/RLS برای مشتری و سازمان دوم را با حساب‌های آزمون واقعی و مجاز کامل کن؛ در زمان ممیزی فقط دو پروفایل فعال (مالک و کارمند) در یک سازمان وجود داشتند.
3. توابع حساس `SECURITY DEFINER` و تنظیمات هشدار امنیتی را موردی بررسی کن؛ بعد از عبور رسمی فاز صفر، طراحی اشتراک صریح افراد را شروع کن.

## موانع
- دادهٔ فعال مشتری یا کاربر فعال از سازمان دوم برای آزمون نقش‌محور وجود ندارد؛ دادهٔ ساختگی برای جا زدن تست موفق ساخته نمی‌شود.
- دسترسی به نشست‌های واقعی با نقش‌های مختلف برای آزمون مستقیم REST هنوز فراهم/مستند نیست.
- هیچ Secret، توکن یا کلید خصوصی در این سند ثبت نشده است.
